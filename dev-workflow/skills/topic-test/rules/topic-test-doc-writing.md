# Rule: Writing the Topic Test Doc

> *Adapt paths/commands to your repository's actual layout and tooling (test runner, dev-server command, logger, DB/Cache CLIs, gateway prefixes).*

Follow the [Shared: Topic Doc Writing Conventions](`${CLAUDE_PLUGIN_ROOT}/skills/_shared/rules/topic-doc-writing-conventions.md`) for Table of Contents, Last Updated, file paths, never-guess, and cross-linking rules — do not restate those here.

## Authoring & Structure

- Every test case states **why it's needed** and includes both **positive** and **negative** expected results.
- Every test case includes **how to run** — exact copy-pasteable command.
- Do not duplicate main/plan doc content — the test doc owns "how to verify" and "what proves it works."
- **The "one doc per open question" rule is in the [shared conventions](`${CLAUDE_PLUGIN_ROOT}/skills/_shared/rules/topic-doc-writing-conventions.md`)** — each OQ lives only in the doc where it was raised; other docs reference it. Applied to the test doc: its Open Questions section lists only **test-specific** questions (those raised while writing the test cases). For questions already tracked in the main or plan doc, reference them (e.g. `main doc OQ N` / `plan doc OQ N`) rather than re-listing them.
- **Required categories: Smoke & Sanity (`SMK-`), Negative Flow (`NEG-`), and Positive Flow (`TC-`).** Generate these by default, every time.
- **Optional categories: Edge Cases (`EC-`) and Error Scenarios (`ERR-`).** Generate a category ONLY when the user explicitly asks for it — never add one unprompted. Omit the section entirely when not requested; do not leave empty placeholders.
- **Performance (`PERF-`) is conditionally required** — it is required when the main doc's Non-Functional Requirements section (e.g. §5.5 in the main-doc template) sets a Performance NFR with a concrete target (e.g. `p95 < 500ms`). When required, generate it by default alongside SMK/NEG/TC. When no Performance NFR is set, PERF remains optional (generate only on request).
- **Regression (`REG-`) is conditionally required** — it is NOT a pure optional category like EC/ERR. It is **required** when the plan doc touches any shared code path: e.g. middleware, shared helpers, utils, config, or any file imported/used by 2 or more modules (adapt the path list to the repo's layout). When required, generate it by default alongside SMK/NEG/TC; do not wait for the user to ask. When the plan touches only self-contained feature files with no shared-path impact, REG remains optional (generate only on request). If the adopting repo wires a deterministic `regression-gate` check in its `.claude/hooks/` (it reads the sibling plan doc's Current Code file paths on `*_TEST.md` edits), that gate enforces this — check before relying on it.
- **Staging Post-Deploy Verification (`STG-`) is conditionally required** — it is NOT a pure optional category. It is **required** when the topic is deployed to Staging (STG) **and** the classification is one of: New feature (heavy), Bug fix (non-trivial), Config/infra change, or Hotfix. When required, generate a `## Staging Post-Deploy Verification` section by default alongside SMK/NEG/TC/REG. It is **optional** for Refactor and Test-only classifications, and **skipped** for Investigation and Minor change. The section contains `STG-###` cases that run against the staging environment (via the API Gateway route prefix, if the deployment uses one — e.g. a `/cr`-style prefix) after deployment, each recording a `**Result:**` line from the staging run. The trigger is the plan doc's Deployment Status table marking STG as Deployed. This is **LLM-enforced** (a deterministic hook may exist in the adopting repo's `.claude/hooks/` — check before relying on it) — see the "Staging Post-Deploy Verification" section in the workflow guide (e.g. `TOPIC_WORKFLOW_GUIDE.md` in the adopting repo's `.claude/docs/`, if present — adapt as needed) for the full policy and the required/optional matrix.
- **Unit Tests (`UNIT-`) are recommended** — not required/gating. Recommended when a plan phase touches function-level logic in the repo's service/helper/util layer (e.g. in one Express.js layout: `server/database/service/`, `server/helpers/`, `server/utils/`, or `server/service/`); skip for pure route/doc/config-only changes. Unit tests are white-box, in-process, infrastructure-free: DB, cache, and external HTTP are mocked via the test framework's module-mocking facility (e.g. `jest.mock`) — no real DB/cache/HTTP, no container infra, no running server. Mock at the seam the repo's services actually use (e.g. in a Mongoose-based codebase, the shared `models` default export — `import models from '../schema'` — supplying stand-in chain methods like `findOne`, `updateOne`, `save`, …); mock external modules (e.g. a structured logger such as `server/lib/logger.js`) where their construction has import-time side effects (worker-thread transports) that would destabilize the suite or pollute output. Colocated test files (e.g. `__tests__/`) mirror the source tree; use the repo's logger helper (e.g. `loggerFor('ComponentName')`) for any diagnostic output, never `console.log`.
  - **Run-order placement (explicit):** the full test-suite command (e.g. `npm test`) runs **after ALL implementation phases are complete** and **before the NEG post-fix pass** — it is an earlier, faster, infrastructure-free layer that does not replace the manual SMK/NEG/TC/REG/STG categories. Do NOT run the test suite between implementation phases (the "no tests between phases" guardrail still holds); the full-suite unit run is a single post-implementation gate. This is **LLM-enforced** (a deterministic hook may exist in the adopting repo's `.claude/hooks/` — check before relying on it) — see the `UNIT` column in the workflow guide's Decision Matrix and execution flow.
  - **Implementation timing & session (explicit):** this doc specifies the `UNIT-###` cases only — the colocated test files themselves are implemented during the plan phase that names them, in a fresh implementation session seeded from the plan + test docs. The canonical rule is the execution rule in [`${CLAUDE_PLUGIN_ROOT}/skills/topic-implement/rules/topic-implementation-execution.md`](`${CLAUDE_PLUGIN_ROOT}/skills/topic-implement/rules/topic-implementation-execution.md`) ("Unit-Test Implementation Timing"); it is not restated here.
- **Smoke & Sanity always runs first** — the fast baseline check that the service and its critical dependencies are up, before any other category.
- **Negative Flow is required TWICE — once BEFORE and once AFTER the feature/fix is implemented.** The BEFORE run (pre-fix) confirms the bug genuinely exists (bugfix) or the behavior is genuinely missing (feature), prior to any code changes. The AFTER run (post-fix) confirms each case now returns the correct rejection instead of the original bug, and that the fix didn't break the validation path. Both runs are required — a test doc with only a pre-fix run is incomplete.
- **Opt-out for topics with no negative-flow surface:** a topic that genuinely has nothing to negative-test (e.g. a read-only enrichment/filter feature with no invalid-input path), or a completed topic the team has decided not to backfill, may skip the negative-flow gate entirely. Add one marker anywhere in the plan doc or the test doc, with a stated reason: `<!-- neg-flow-gate: exempt — <reason> -->`. An exemption marker with no reason is itself flagged by the gate (if the adopting repo wires the `neg-flow-gate` hook in `.claude/hooks/` — check before relying on it).

## Environment Scope

- Tests run on **exactly two environments — Local and Staging only.** No other environment (Development, Production/PRD, or any other) may be used for test execution. If the adopting repo wires a deterministic `env-scope` gate in `.claude/hooks/` on `*_TEST.md` edits, it enforces this — check before relying on it.
- The **Test Environment** section must have **separate `### Local` and `### Staging` subsections.** Each subsection documents the environment-specific details that differ between them. **Never hardcode the actual hostnames/URLs in this rule file or the template** — use placeholders (the `<UPPER_SNAKE_CASE>` placeholder convention) and fill in the real values per topic. If a required value (gateway domain, local port, DB prefix, gateway header) is not known from the codebase or the user, mark it `<!-- TODO: confirm -->` and ask the user rather than guessing.
- **Opt-out for non-runnable test docs:** some `*_TEST.md` files are not an executable Local/Staging test suite at all (e.g. an investigation/known-issues doc). Such a doc may skip this gate entirely by adding one marker anywhere in the file, with a stated reason: `<!-- env-scope: exempt — <reason> -->`. An exemption marker with no reason is itself flagged by the gate (if wired in the adopting repo).
  - **Local:** the service started locally by the user, direct URL `<LOCAL_API_URL>` (no gateway prefix), database/cache CLI access if your stack provides one (e.g. `redis-cli` / `mongosh` to `<LOCAL_REDIS_HOST>`, `<LOCAL_DB_HOST>` when the stack uses Redis/MongoDB), database names without the staging prefix, seed/reset commands available.
    - **Reuse the already-running local service — NEVER start a duplicate.** Before running any local test, first check whether the service is already up on its local port (e.g. `curl -s -o /dev/null -w "%{http_code}" http://localhost:<port>/...` — expect `200`/`401`, not `000`). If it responds, **reuse it as-is**; do not run the dev-start command again. **If the repo's dev-start command kills any existing instance on the port first** (e.g. a `prestart` script running a port-killer on the local port), running it while the user's instance is up destroys their service and causes `HTTP 000` / connection-refused on subsequent requests. A test that suddenly returns `000` is more likely caused by a duplicate dev-server start killing the port than by the code crashing — check the port first before assuming a code bug.
    - **If a restart is needed, ask the user to do it manually.** Do not restart the local service yourself. Ask the user to restart it (they know their run practice, e.g. the repo's dev-start command from the repo directory), and only continue testing after the user confirms the service is back up. Exception: if the restart flow is complicated and the user has explicitly authorized it, the AI may kill the current running local service and restart it following the user's documented run practice — but only with that explicit authorization.
    - **Config source & sensitive files (stack-dependent):** services typically load environment-specific config from **gitignored** files (env files, profile files, user-secrets stores — the canonical per-stack file list is in the [Shared: Sensitive File Scope](`${CLAUDE_PLUGIN_ROOT}/skills/_shared/rules/sensitive-file-scope.md`) rule, which the AI follows: it **never reads** them). Local config vars (e.g. an external-service API key) go in those gitignored files, never in committed config files. Every placeholder or env value the AI needs (for docs, "how to run" commands, or local test runs) comes from the adopting repo's placeholder reference doc (e.g. `docs/PLACEHOLDER_REFERENCE.md` — adapt the path); the human sets the real values in the actual environment. If a needed value is not in the reference doc, ask the human to add it — do not look for it in sensitive files.
    - **Log level:** the repo's structured logger (e.g. a pino-based `server/lib/logger.js` with a `loggerFor('ComponentName')` helper) typically defaults to `debug` for non-production runs (`LOG_LEVEL` env var overrides it, if supported). For local debugging, `log.debug(...)` output is visible in the dev-server terminal — no need to set `LOG_LEVEL` unless filtering. **Never use `console.log` for debugging** — use `log.debug`/`log.info` via the repo's logger helper so output is structured and redacted. When a test needs to inspect runtime state, add a temporary `log.debug` (not `console.log`) and read it from the dev-server terminal.
  - **Staging:** the API is reached **via the API Gateway** — the endpoint path **must include the gateway's route prefix** (e.g. a `/cr`-style prefix that the Gateway strips before forwarding `/api/...` to the service — confirm the actual prefix for the target deployment), URL `<STG_GATEWAY_URL>/<gateway-prefix>/api/...`, VPN or office network required if the gateway is internal, database/cache read-only via their web/desktop management UIs (e.g. Atlas / Redis Insight if the stack uses Mongo/Redis — no CLI), databases prefixed with the staging prefix, and the required gateway role header (e.g. `X-User-Role: guest` — default; change only if the topic needs a different role).
- Staging is **read-only** — the Setup / Reset block applies to Local only; note this in the template.
- **Prohibited operations on Staging (never run these):** any CLI or direct connection to staging databases or caches (e.g. `mongosh` / `redis-cli` / any direct connection, if the stack uses Mongo/Redis), any write/delete/update to staging data, and any direct connection to the staging database using credentials from staging env files or any env file. Staging databases are inspected **only** via their read-only management UIs (e.g. the **MongoDB Atlas web UI** for Mongo, **Redis Insight** for Redis) — manual, human-performed steps. The AI must **never** attempt to connect to or query staging infrastructure programmatically. If a test case requires inspecting staging data, the test doc must provide **step-by-step manual instructions** for the human to perform in the management UI, and the AI must ask the user to run them and report back the result.
- "How to run" commands in test cases must target **either** Local or Staging explicitly (e.g. use the local URL for local runs, the gateway-prefix URL for staging runs) — never an ambiguous or environment-agnostic URL.
- **Staging Post-Deploy Verification** — when the topic is deployed to STG and the classification requires it (see the `STG-` rule above), the test doc must include a `## Staging Post-Deploy Verification` section. Its `STG-###` cases run **after** deployment, against the staging environment only (via `<STG_GATEWAY_URL>/<gateway-prefix>/api/...` with the gateway role header). Each case records a `**Result:**` line from the staging run. These cases are distinct from the Local-runnable cases — they validate the deployed behavior behind the real API Gateway, with staging config, staging databases/caches, and the staging network path. Do not run Local-only cases (e.g. ones requiring direct database/cache CLI access) against staging — staging is read-only.
- **Manual-check steps for staging data inspection:** any `STG-###` case that inspects staging databases or caches must include a **"Manual Check (<management UI>)"** subsection with exact click-path steps for the human to follow in the web UI (e.g. "Atlas → Browse Collections → `<stg-prefix><database>` → `<collection>` → inspect a document for fields X, Y, Z"). The AI must not attempt to run these steps itself; it prepares them and asks the user to execute and report back.

## Post-Test-Run Updates

- Update the test doc immediately after every test run — do not batch updates. This keeps it the live source of truth for future runs.
- **Every NEG-### case records TWO result lines** — `**Result (pre-fix):**` (recorded during Phase 1, before the fix) and `**Result (post-fix):**` (recorded during Phase 2b, after the fix). A NEG case with only one result line is incomplete; the test doc is not feature-complete until both lines are filled.
- If a test fails, document the failure in the result table (mark ❌ FAIL) and capture the error signature (log lines, HTTP response, stack trace) in the notes before attempting any fix — investigate the root cause, do not attempt blind fixes.
- The result line reflects the **actual outcome of the latest run**, not the intent of a fix. After a fix, re-run the test: mark ✅ PASS only if that re-run genuinely passes. If it still fails, keep ❌ FAIL and iterate — the number of fail→fix cycles is irrelevant; only the real outcome of the most recent run is recorded. Append a new run log entry for each attempt. If a fix required changes to the "how to run" steps, update those too.
- **Fix the commands first** — if a "how to run" step was incorrect or incomplete, correct it before recording the result. The next person (or you) should be able to follow the doc and get the same result.
- **Document anti-patterns you encountered** — if you hit a port conflict, stale state, or config gotcha, add it as a fail condition or note so others don't waste time on it.
- **Run log is append-only** — never delete or edit past run log entries. Add a new row for each run.
